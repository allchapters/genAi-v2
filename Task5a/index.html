    Task 5: File Search using Gemini Online Retrieval Augmented Generation (RAG)

    File Search using Gemini
    Introduction

    Google have introduced a new File Search Tool, a fully managed RAG service built into the Gemini API that can be called with a single API example:https://generativelanguage.googleapis.com/v1beta/fileSearchStores. More info can be found here.

    In the earlier tasks, we learned how to build our own RAG pipeline using LangChain and vector stores, which gives us a lot of flexibility and control. With Gemini File Search, we now have another option: a managed RAG service where Google handles chunking, indexing, embeddings, and retrieval for us. Instead of replacing the old approach, this simply gives us a choice. For some use cases, building RAG yourself will still make sense for others, using Gemini File Search can reduce complexity so you can focus more on your application and AI-by-design decisions rather than the plumbing.

    With the File Search Tool, things get much simpler. Instead of managing chunking, embeddings, and retrieval yourself, you just create a file search store and upload your documents. Gemini takes care of splitting, embedding, indexing, and retrieving the right content when you ask a question. This hides the retrieval pipeline so you can focus on your app. File Search gives you an easy, scalable way to ground Gemini on your own data, so answers are more accurate, relevant, and easier to verify. In practice, you simply upload your files, create a store, and let the API handle the rest. A nice bonus is pricing: you only pay for embeddings (depending on the embedding model you use. Default model gemini-embedding-001 at a fixed rate of $0.15 per 1 million tokens ) and for the LLM tokens that are in context. File storage and query-time embeddings are free according to Gemini documentation. For more details on embeddings and pricing, see: More info on embeddings and pricing. For more details on tokens, see: More info on tokens.

    At the time of writing this guide the following models support File Search: gemini-2.5-pro & gemini-2.5-flash.

    The File Search capability in the Gemini API is a fully managed Retrieval-Augmented Generation (RAG) feature. It takes care of storing your files, splitting them into chunks, generating embeddings, and automatically adding the most relevant context to your prompts.

    You might wonder if this comes with a high cost. Actually, it doesn’t. File storage and on-demand embedding generation during queries are free. You’re only charged for the initial indexing of your content, at a flat rate of $0.15 per 1 million tokens, based on the embeddings created.

    In this tutorial, we’ll go through the end-to-end workflow of using File Search with a Python script. You’ll learn how to:

    1. Create a File Search store

    2. Look up an existing store by its display name

    3. Upload files into the store

    4. Use advanced upload options such as custom chunking and metadata

    5. Run a standard RAG-style generation query

    6. Clean up by deleting the File Search store when you’re done

    Here we’re uploading our PDF(Geminidect) into the selected File Search store and waiting for Gemini to finish indexing it. The upload_to_file_search_store call sends the file (with the display name we set, and optional custom chunking if you uncomment that part), and it returns a long running operation. The while loop simply polls this operation every few seconds until the upload and indexing are complete. Once it’s done, we print a confirmation so you know your document is now ready to be used in File Search queries.

    • We’re configuring the File Search tool that the Gemini model will use. We create a Tool object with a FileSearch configuration and point it to our file_search_store_name, which tells Gemini which store (and documents) it’s allowed to search. We don’t need to manually retrieve chunks or run separate search calls, we just tell the Gemini model to use the file_search tool and point it to our store name. When the model needs more information, it will automatically search the store, pull the most relevant chunks, and ground its response on that content. The print(file_search) line simply shows the tool configuration so you can confirm everything is set up correctly.

    SUMMARY
    You’ve effectively built a complete, managed RAG pipeline using Gemini File Search. You created a File Search store, uploaded and indexed a PDF, waited for the embeddings and index to be built, then wired that store into a file_search tool and attached it to a generate_content call. From that point on, Gemini handled retrieval for you, it converted your question into an embedding, semantically searched your File Search store, pulled the most relevant chunks, and grounded its answer on your document without you ever manually fetching or passing chunks yourself. This is exactly what the File Search tool is designed for a simple, integrated way to ground Gemini on your own data so you can focus on prompts and product logic instead of building and maintaining your own vector database and RAG stack.
